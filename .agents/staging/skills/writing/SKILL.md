# writing

読みにくい文章の原因は語彙ではなく構造にある。
難しい言葉を平易にしても読みやすくならない。文の切れ目と情報の置き場所を直す。

指標は診断であって合格判定ではない。数値を下げること自体を目的にすると、出典や条件を削って正確性を落とす。判断は人が持つ。

## command

`/writing <subcommand>` の形式で起動する。

- `<path>`
  - 下記「手順」を最後まで実行する
- `check <path>`
  - 手順 1-5 だけを行う
  - 指標と症状を報告する
  - 書き換えない
- 引数なし
  - 対象の文書を確認してから進める

## repo 固有の値

操作対象の repo の root に `.agents/bindings/writing.md` があれば最初に読む。root は `git rev-parse --show-toplevel` で求める。

binding は次を定める。

- 対象 file の manifest の作り方
- 編集してはいけない path
- file の種類ごとに通す gate
- コードコメントを対象にする directory
- その repo だけが持つ文書形式

binding が無い repo では次の既定で動く。

- 対象は依頼で名指しされた file だけにする
  - directory を名指しされた場合は、対象 file の一覧を提示して確認を取る
- 編集してはいけない path は「壊してはいけないもの」の対象外に従う
- gate は「gate」節の既定を使う
- コードコメントは、依頼で名指しされた file のものだけを対象にする
- repo 固有の文書形式は無いものとして扱う

## 症状

ある repo の文書を 2026-08-06 に層別に実測した。
「しっかり」「非常に」のような空疎な副詞はほぼ無い。読みにくさは構造に出る。

太字と括弧は散文行数、長文比は文数を分母にする。見出しの括弧内が閾値である。

| 層         | 太字 (0.10) | 括弧 (0.30) | 長文比 (0.30) |
| ---------- | ----------- | ----------- | ------------- |
| wiki の記事 | 0.00        | 0.37        | 0.51          |
| skill 文書 | 0.21        | 0.51        | 0.25          |
| README     | 0.03        | 0.62        | 0.29          |

層ごとに出る症状が違う。

- skill は太字が過剰
- README は括弧が過剰
- wiki は長文が過剰

1 つの閾値で全部を裁かない。

太字が 2 行に 1 回来ると、読み手は強調を無視し始める。
太字はここだけ読めば事故を防げるという非常口であって、話者の語気ではない。

括弧が多い文章は、本文に入れるほどではない情報を書き手が捨てきれていない。
中身が補足なら本文へ格上げするか独立した文にする。日付や数値のような事実なら残す。
`measure.py -v` が中身を列挙するので、1 つずつ見て決める。数を減らすために消さない。

日本語は接続助詞でいくらでも伸びる。1 文に条件と理由と例外が詰まると追えなくなる。
60 文字を超えたら係り受けの切れ目で割る。

## 測れない症状

指標は入口でしかない。次は読んで判断する。

- 同語反復
  - 同じ語が 3 文以内に 3 回出ていないか
- 無内容な規範文
  - 「適切に」「必要に応じて」を消して意味が変わらないなら情報ゼロ
- 要約と本文の重複
  - 冒頭の要約が本文の言い換えになっていないか
- 機械的な並列
  - 同じ長さ同じ構造の箇条書きは、分類していない兆候
- 結論の反復
  - 節の最後で同じ結論を言い直していないか
- 文書自身を話題にした文
  - 判定は 1 つで足りる。その文が更新するのは「状況」か「文書」か
  - 状況を更新する文は、対象の事実 / 数値 / 判断の状態を新しく伝える。残す
  - 文書を更新する文は、この節がどう見えるか、次に何を書くかだけを伝える。削除する
  - 例は「ここまでは概念の説明に見えるだろう」「次は〜を見る」「〜の列挙はしない」である
  - 削除して前後が繋がるなら、それで終わる。論理が飛ぶ場合は、その文が指していた内容を対象側の事実として書き直す
  - 短く断定調へ整形すると、拍が効いた決め台詞に見えて残りやすい。短さとリズムは残す理由にならない

受動態は gate にしない。日本語では主語省略や客観表現と区別できない。

## 構造のルール

書く文章と直す文章の両方で、次のルールを徹底する。
ここに並べたのはルールの名前だけである。ルールの本文と例外、悪い例と直した例は [rules.md](rules.md) にある。書き直す前に必ず読む。

- リスト記法内で改行しない
- リストの見出し項目に本文を続けない
- リスト項目を接続助詞で繋げない
- 読点で改行しない
- 改行は文と話題の切れ目に置く
- 1 段落 1 話題にする
- だ、である調を徹底する
- ラベルと体言止めを文にする
- 複数あるならリストで列挙する
- できるだけ表は使わない
- コードコメントにも同じ構造ルールを適用する

## 直し方

- 1 文 1 主張にする。条件と理由と例外が同じ文にあるなら分ける
- 結論から書く。「〜のため、〜なので、〜する」ではなく「〜する。理由は〜」
- 具体を先に書く。「注意が必要」ではなく「ここを忘れると gate が黙って通る」
- 数字と固有名詞は残す。それが読める文書と読めない文書を分ける情報量になる
- 補足の括弧は連体修飾に開く。「X (自前の lib)」ではなく「自前の lib である X」、「X (`fmt:check` に含まれる)」ではなく「`fmt:check` に含まれる X」と書く
- 括弧の中身が本文より重要なら、括弧をやめて独立した文にする
  - 例は「互換性 100% に到達した (パス率は 99% で、残る失敗は全て相手側の既知バグ)」である
  - 読み手が知りたい落差が括弧に隠れている。「100% に到達した。パス率そのものは 99% である。残る失敗は全て相手側の既知バグだった」と開く
- 断定を並べ続けない。長い断定文が 3 つ以上続いたら、短い文を挟んで足場を作るか、そこで一度止める
  - 挟む短い文は、既にある事実の分割か、既にある判断の言い直しからしか作らない
  - 材料が無ければ何も足さず、長い断定の連続のまま残す。足場のために文を捏造すると「文書を更新するだけの文」の再生産になる
- 同じ構造の項目が 4 つ以上並び、項目ごとに複数の属性を見比べるなら表にする
- 箇条書きだけの文書にしない。判断の理由は散文でしか書けない

## 壊してはいけないもの

事実を変えない。数値もパスもコマンドも手順の順序も動かさない。
書き直しは意味を保存する変換であり、内容の再検討ではない。
疑問が出たら直さずに指摘として報告する。

情報を落とさない。制約や例外を削ると次に読む人が事故る。
閾値を満たすために情報を削ったら、その書き直しは失敗である。

読み物の技法を持ち込まない。答えを保留して先を読ませる装置は、この skill の対象文書には有害である。
未回収の問い、あとで裏切られる思い込み、書き手の告白、読者への呼びかけがそれにあたる。
README / skill / plan は契約文書で、wiki や reference は引く道具である。どちらも、読み手はその場で答えを得て離脱してよい。
「文書自身を話題にした文」と「1 段落 1 話題」と「括弧の解放」は、2026-08-15 に外部の規範 ([cognitive-rhythm-writing](https://gist.github.com/k16shikano/eb2929f13ed19c97188393d297be8432)) から取り込んだ。取り込んだのは、実際の文書で効いたこの 3 つと拍だけである。

AGENTS.md / CLAUDE.md とその実体の file、および skill は、書いた文言がそのまま agent の行動仕様になる。これらは契約なので扱いを厳しくする。

- 節ごとに変更前の命題を書き出し、変更後も 1 対 1 で残ることを確認する
- 「〜しない」を「〜は避ける」に弱めない。優先順位と既定値と例外条件と owner と順序を保つ
- link の宛先を変えない
- 書き直せない曖昧な文は、削らずに owner へ判断を返す
- 他の変更と混ぜない。commit を頼まれているなら独立した commit にする

既定の対象外は次のとおり。binding があれば、その定めを加える。

- 日付付きの plan のような歴史の記録
  - 当時の判断がそのまま価値を持つ
  - plan の catalog は対象にする。歴史ではなく生きた文書である
- 外部由来の snapshot と vendoring された file
  - 更新で上書きされる
- 外部管理の skill
  - `skills-lock.json` にある skill がこれにあたる
  - 更新で上書きされる
- 生成物と lockfile と `node_modules/**`
  - 手で書くものではない
- 著者の文体を保つべき本文
  - 記事や原稿がこれにあたる
  - repo に校正用の skill があれば、そちらが担当する
- commit message
  - `commit-message` skill が担当する
- 英語主体の文書
  - 指標は日本語の散文を前提にしている

## 手順

1. binding を読み、manifest を作る
   - ディレクトリを直接渡すと意図しないファイルが混ざる
   - 1 ファイルだけを直すときは manifest を作らず、そのファイルを渡す
   - 件数と中身を確認したら以後変更しない
2. baseline を記録する。対象に `measure.py` を掛ける
3. chunk を取る。人が diff を読み切れる大きさにする。目安は 5 ファイル、短い page が並ぶ文書なら 10 ページ
4. 診断する
   - `measure.py -v` の結果を読む
   - [rules.md](rules.md) の構造のルールを当てる
5. 「測れない症状」を当てる
6. 節ごとに書き直す。1 回の編集で全体を書き換えない
7. `git diff` の消えた行を 1 行ずつ見る
   - 数値、パス、コマンド、link の宛先、否定形、既定値、例外条件を特に見る
   - syntax の gate は全て通るのに条件だけが落ちる、という壊れ方をする
8. その chunk の gate を通す。chunk ごとに通し、最後にまとめてではない
9. 次の chunk へ戻る。全部終わったら対象全体に gate をもう一度通す

完了の条件は 3 つある。

- gate が全て通ること
- `git diff` に事実の欠落がゼロであること
- 閾値の超過を残すなら、その理由が報告に書かれていること

## gate

binding が gate を定めていれば、それを通す。次の既定は binding の有無にかかわらず適用する。

- すべて
  - repo の AGENTS.md / CLAUDE.md が定める format 検査
  - 定めが無ければ `git diff` の確認だけを行う
- AGENTS.md / CLAUDE.md とその実体の file
  - symlink が壊れていないこと
- skill
  - frontmatter の `name` と subcommand 名が不変であること
  - 手順の command が実在すること
- コードコメント
  - repo が定める型検査や lint が通ること
  - `git diff` で、コメント行以外の差分がゼロであること

## コードコメント

対象にする directory は binding が定める。binding が無ければ、依頼で名指しされた file のコメントだけを対象にする。

対象はコメントであって、script が生成したり処理したりしている content 自体ではない。生成物も対象にしない。

`measure.py` は Markdown 前提のパーサのため、コードコメントの診断には使えない。当たり付けは grep で行う。

```sh
grep -rEn '^\s*(//|#).*、\s*$' <dir> --include='*.ts' --include='*.sh'
grep -En '^\s*#.*、\s*$' <file>
```

Claude Code の `grep` は ugrep で、`--include` が明示した path にも効く。拡張子が混在する directory と単体の file で command を分ける。

## measure.py

計測は `measure.py` が持つ。grep と句点 split では測れない。
Markdown の link や code span の括弧を数えてしまい、空行や fence を跨いで段落が 1 文に連結されるからである。

`measure.py` はこの SKILL.md と同じ directory にある。cwd からの相対 path ではなく、その directory の絶対 path で起動する。

```sh
python3 <この skill の directory>/measure.py -v <path>...
```

既定は report-only で exit code は常に 0 である。`--gate` は opt-in であり、書き直しの完了条件に使ってはいけない。

19 個の fixture が境界を固定している。`measure.py` を触ったら `--selftest` を走らせる。CommonMark の完全な実装はしない。誤検出が出たら fixture を足して直す。
