前提となる用語

中間 CA
ルート認証局 (ルート CA) から委任を受けて、実際にサイトの証明書に署名する認証局。ルートが信頼されていれば、その下の中間 CA が署名した証明書も信頼される。
トラストストア
OS やプログラムが「信頼するルート CA」の一覧として持つファイル。このサーバには system ストア (/etc/ssl/certs/ca-certificates.crt、apt 管理) と Homebrew ストア (cert.pem) があり、さらに node / deno / bun / Claude Code のように自分専用の一覧を内蔵するものがある。
クロス署名
同じ中間 CA を別のルートからも署名しておく仕組み。今回の中間 CA は emSign 自身のルートと Sectigo の AAA Certificate Services の両方から署名されており、どちらか片方でも信頼していれば偽証明書が通る。
TRUSTED / REJECTED / ERROR
本 report の判定語。TRUSTED は漏えい CA 経由の証明書を受け入れた (悪い)、REJECTED は証明書エラーで拒否した (良い)、ERROR は DNS や timeout など証明書と無関係な失敗で、合否の根拠にならない。
陽性対照
正しい証明書を持つホスト (valid-isrgrootx1.letsencrypt.org) への接続。これが TRUSTED にならないクライアントは「何でも拒否している」だけなので、REJECTED を成果として数えない。
GATE
check.sh の総合判定。必須 16 client 全てについて「行数がホスト数と一致、ERROR 0、陽性対照 TRUSTED、許容リスト以外は TRUSTED 0」を満たしたときだけ PASS。

何が起きたか

2026-10-20 に公開されたアドバイザリ (emudhra.we-have-a-problem.com) によると、eMudhra が 2025-04 に作成した中間 CA 証明書 8 件は鍵生成に欠陥があり、公開されている証明書だけから秘密鍵を復元できる。つまり誰でも任意のサイトの偽証明書を作れる。CA は失効済みだが、失効情報を見ないコマンドラインツールやライブラリは、ソフトウェア側の更新が無いと偽証明書を受け入れ続ける。

サイトの証明書
攻撃者が任意のホスト名で発行できる
eMudhra 中間 CA (8 件)
秘密鍵が証明書から復元可能。Sectigo によるクロス署名 8 件も同じ鍵
emSign ECC Root CA - G3
Mozilla / Apple / Chrome / Microsoft 全てが収録。このサーバで唯一露出していたルート

もう一方のルート AAA Certificate Services 経由は、deno 2.9.7 を除く全クライアントが対策前から拒否していた (Mozilla / Chrome が削除済みのため)。

このサーバの外向き通信は、Let's Encrypt、Cloudflare API、npm / Go / PyPI のレジストリ、GitHub、api.anthropic.com などに及ぶ。経路上の中間者攻撃という前提で確率は低いが、鍵は公開状態で、対策はストアとランタイムの更新だけなので、先延ばしにする理由が無かった。

当初は apt から始める順序だったが、この環境の agent は sudo を使えないため、agent が実行できるもの (Homebrew、mise、rustup) を先に行い、sudo 手順は Jxck が実施した。結果的に apt は 06:51 の unattended-upgrades が先に適用した。

どう測ったか

「ストアから証明書が消えた」だけでは、自前の一覧を内蔵するランタイムが直った証拠にならない。そこで、漏えい CA 経由の証明書を実際に提示するテストホスト 12 件 (アドバイザリ提供。dv / ov / ev の 3 種 x 中間 CA g3b / g3c x ルート emSign / AAA) に、このサーバの TLS クライアント 16 種で実際に接続し、結果を 3 値 (TRUSTED / REJECTED / ERROR) に分類するスクリプト (check.sh v2、plan に埋め込み) を使った。

  • 必須 client 16 種: curl (brew / system)、wget、node、bun、deno、go、python (brew / system)、ruby、git (brew / apt)、pnpm (per-host と native-store)、openssl verify (system ストア / brew ストア、オフライン)
  • 陽性対照を毎回含め、「全部拒否」を成果と誤認しない
  • ERROR を合否から除外し、gate は ERROR 0 を要求する。経路の不調で REJECTED に見えることを防ぐ (fail-closed)
  • 行数検査: client ごとに行数 = ホスト数を要求し、probe の空振りを検出する (レビュー round 2 で追加)
  • オフライン verify: openssl verify -CAfile でチェーン 12 本を両ストアに対して検証する。rustup / pnpm が読むハッシュディレクトリ (/etc/ssl/certs/<hash>.0) も同時に検査できる
  • 個別 probe: mise の汎用 HTTP (MISE_URL_REPLACEMENTS でテストホストへ向ける)、certbot snap の httpx、稼働中 claude プロセスの実体 (/proc/<pid>/exe を strings で検査)

Bun は EXPECT_TRUSTED=bun で TRUSTED を許容した。stable に修正版が無く (PR #46159 は main のみ)、SSL_CERT_FILE も無視するため、このサーバ上では直せない。Bun 製サービス (mozaic.fm / vtt.mozaic.fm) は外向き TLS を行わないことをコードで確認している。

発見

  1. 修正済みストアだけで取得する方式は mise に効かなかった。 3-3 では、未修正の system ストアに依存せず新版を取るため、SSL_CERT_FILE で brew ストアだけを指定する予定だった。実施前の probe で mise 2026.10.17 がそれでもテストホストに 200 を返し、system ストアも読み続けると分かった。代わりに、修正済みストアを使う Homebrew curl で同じ配布物を独立に再取得し、インストール済みツリーと全ファイルの内容ハッシュを比較した (node 4743 件、go 15657 件、deno と rustup はバイナリの sha256)。全件一致したので、取得経路の改ざんは無かったと判断した。
  2. deno 2.9.8 はエラーの形が変わり、初回は ERROR 判定になった。 12 ホスト全てを CertDistrusted で拒否していたが、メッセージが TypeError: fetch failed と cause に分かれたため、check.sh の判定に cause を含める修正を入れて再確認した。3 値判定と ERROR の除外が無ければ、これを「拒否した」と誤読していた。
  3. pnpm は apt 前は無応答、apt 後は即時拒否になった。 修正前は emSign 系ホストが pnpm に対して応答を返さず、timeout で ERROR (fail-closed)。apt 後は TLS 失敗が即時に返り 12/12 REJECTED になった。plan の予測どおりで、pnpm が system ストアを読んでいる直接証拠になった。
  4. 稼働中の Claude Code は未修正版のままだった。 ディスク上の claude は自動更新で 2.1.306 (emSign 0 件) になっていたが、plan を書いていたセッションの /proc/<pid>/exe は起動時の 2.1.296 (emSign 2 件) を指していた (レビュー round 2 の指摘)。セキュリティ修正を含む更新のたびに、長時間稼働のセッションは再起動が要る。
  5. Homebrew cask の Claude Code は管理外だった。 Linux では Brewfile (if OS.mac? 内) にも update.sh (formula のみ) にも含まれず、手で入れたものが PATH 上で shadow されていた。native 版 (~/.local/bin/claude、install/install-claude.sh で導入) に一本化し、cask は撤去した。
  6. apt は手動実施の前に自動適用された。 apt-daily-upgrade.timer の次回が 06:50 であることを plan に書いていたとおり、06:51 に unattended-upgrades が適用した。sudo 手順を人に渡す前に、自動化の予定時刻を確認しておく価値があった。
  7. 最終 check.sh の 1 回目は go の 1 ホストだけが接続リセットで ERROR になった。 証明書と無関係な経路エラーなので、同ホストを単発で再 probe (2 回とも REJECTED) したうえで全体を再実行した。再実行 (18:38-18:42) は必須 16 client 全てが ERROR 0 で GATE: PASS となり、これを最終結果とした。
