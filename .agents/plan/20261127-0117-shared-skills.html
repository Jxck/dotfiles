前提となる用語

skill
agent に渡す手順書。SKILL.md という file に、いつ使うかと、どう進めるかを書く。Claude Code と Codex の両方が読む。
subagent
作業の一部を任せる別の agent の定義。使う model と役割を file に固定しておく。
global と repo
skill の置き場所の 2 つの層。global は home directory から読まれ、全ての repo で見える。repo はその repo の中でだけ見える。
binding
global の skill が、ある repo で使う固有の値を書いた file。置き場所は <repo>/.agents/bindings/<skill>.md である。検証 command や編集してはいけない path を書く。
配線
tool が skill を探す場所から、実体の directory へ張る symlink のこと。

移設前に何が困っていたか

よく使う skill は mozaic.fm の中にだけあった。jxck.io で同じ作業をしても、その skill は使えなかった。写して持ち込むと、直すたびに 2 箇所を直すことになる。

dotfiles にも skill の置き場所はあったが、Codex 向けの配線が崩れていた。調べると、17 個のうち 11 個は symlink ではなく古い複製で、2 個は Codex から見えていなかった。

どういう仕組みにしたか

正本を 1 つにして、home から配る

汎用の skill は dotfiles にだけ置く。各 repo へは写さない。home directory の symlink が dotfiles を指すので、1 箇所を直せば全ての repo に効く。

repo に写す方式や、plugin にして配る方式も比べた。使うのが 1 人で、端末が Mac と VPS の 2 台なら、更新のたびに各 repo で作業が要る方式は手間の方が大きい。

repo ごとに違う値は binding に出す

同じ skill でも、repo によって違う部分がある。たとえば sync は、rebase の後に通す検証 command が repo ごとに違う。この部分を skill の本文から外し、各 repo の binding に書いた。skill は最初に binding を探し、無ければ既定の動作をする。

同じ名前を両方の層に置かない

Claude Code は、同じ名前の skill が global と repo の両方にあると、global を使って repo 側を黙って隠す。気付かないまま repo 側の規約が効かなくなる。これを防ぐため、同じ名前を両方に置くことを禁止し、検査する command を作った。

どう確かめたか

skill は文章なので、置いただけでは正しく動くか分からない。そこで、使い捨ての repo を作り、新しい agent の session に skill を実際に起動させて、結果を file と git の状態で確かめた。binding がある場合と無い場合の両方を試した。

発見

dotfiles に置いた瞬間に、元の repo の同名 skill が隠れる

試した
公式の文書で、同じ名前の skill が複数の場所にあるときの優先順位を調べた。
結果
Claude Code では home 側が repo 側に勝つ。repo 側から上書きする方法は無い。
影響
整理した skill を先に dotfiles へ置くと、binding がまだ無い状態で元の repo の規約が効かなくなる。そのため、まず skill として読まれない場所に置いて内容を固め、binding を配ってから正本の場所へ移した。

Codex は ~/.agents/skills を読む

試した
使い捨ての home directory を作り、~/.agents/skills を dotfiles への symlink 1 本にして Codex を起動した。
結果
17 個の skill が全て見えた。同じ実体を複数の経路で指しても、重複は出なかった。
影響
skill ごとに symlink を張る処理が不要になった。古い複製が残る原因もここにあったので、処理ごと削除した。

配線の script は、既存の directory を消しうる作りだった

試した
Codex が、使い捨ての home directory で従来の script を実行した。
結果
先に置いておいた file が消え、終了 code は成功だった。
影響
script を直した。変更の前に全ての link 先を検査し、想定と違うものが 1 つでもあれば、何も変えずに失敗する。VPS で何も変更しなかったのは、この検査が働く状況だったためである。

mozaic.fm の format 検査は、skill を対象にしていなかった

試した
format 検査の設定と、文字の検査 script の除外一覧を読んだ。
結果
どちらも skill の directory を除外していた。元の skill は「この検査が gate になる」と書いていたが、実際には検査されていなかった。
影響
binding には、検査される範囲とされない範囲を事実どおりに書いた。

作業中に、確認用の command が dotfiles で実行される事故があった

起きた
使い捨ての repo を作る command の先頭が失敗し、続きが dotfiles の directory で走った。README.md が上書きされ、意図しない commit が 3 件できた。
復旧
他の変更が無いことを確かめてから、直前の commit に戻した。push はされていない。
原因
この端末では rm が別の command の別名になっていて、消す対象が無いと失敗する。失敗しても続きが走る書き方をしていた。
対策
以後は、1 つでも失敗したら止まる script にまとめ、書き込む前に場所を検査するようにした。

残っていること

VPS への反映

VPS では ~/.agents/skills が実体のある directory で、find-skills という skill が 1 つ入っていた。消してよいか判断できないので、VPS では何も変更していない。

次の順に行う。順序を守らないと、VPS の mozaic.fm から一時的に skill が消える。

  1. find-skills を残すか決める。残すなら dotfiles に取り込み、不要なら ~/.agents/skills を別名に退避する。
  2. dotfiles を pull する。
  3. bin/slink.sh を実行する。これで subagent も使えるようになる。
  4. ~/.codex/skills に残る古い symlink 17 本を退避する。
  5. mozaic.fm と jxck.io を pull する。mozaic.fm の作業 directory は本番の配信に使われているので、いつもの手順で行う。
