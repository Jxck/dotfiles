### 2. 方式の比較と選定

| 方式 | 正本 | 長所 | 短所 |
|---|---|---|---|
| A. user scope (採用) | dotfiles `.agents/skills` を home から symlink | 配線 0。同じ checkout では編集が即時に全 repo へ効く。Claude / Codex 共通。既にほぼ出来ている | 端末依存 (dotfiles の無い環境、cloud session、CI、他の contributor には届かない)。repo と skill の版が連動しない。別端末へは pull が要る |
| B1. コピー | 共有 repo から各 repo へコピー (`npx skills add` + lock) | repo が自己完結。cloud / CI でも動く | repo 数だけコピーが生まれ、更新の伝播が手作業になる |
| B2. submodule | 共有 repo を各 repo に submodule で入れる | 正本は 1 つのまま repo ごとに版を pin できる。自己完結 | 更新のたびに各 repo で submodule を進める作業が要る。編集は即時に効かない |
| C. plugin marketplace | dotfiles を marketplace 化し repo の `settings.json` で opt-in | repo 単位の opt-in。版管理と配布の仕組みがある | Claude と Codex で plugin 形式が別。正式名が `/<plugin>:<skill>` になる。cache へのコピー配布で clone ごとに install が要る。cloud session では repo が宣言した marketplace は追加されない |
| D. repo から dotfiles への絶対 path symlink | dotfiles | 見かけは repo 内にある | 端末の path に依存し、他環境で壊れた symlink になる |

A を選ぶ理由。

- 対話 session を使うのは owner 1 人で、agent を動かす端末は全て dotfiles を導入済みである (TBD-2)
- 要求は「一箇所を直せば全 repo に効く」ことであり、A だけが同じ checkout での即時反映を満たす
- B2 と C の版管理と opt-in は、利用者や実行環境が増えたときの機能である。3 repo / 1 人では、更新のたびに発生する作業の方が大きい
- 「全 repo に全 skill が見える」は、Claude では repo の `skillOverrides`、Codex では `[[skills.config]]` の `enabled = false` で隠せる (この plan では設定しない)

A で届かない経路の扱い。

- 非対話の実行経路 (wiki re-ingest の子 process) は global skill に依存させない。必要な規則は repo 内の file に書き切る (TODO 1-5)
- 自己完結が必要な経路が今後増えたら、その経路だけ B2 を併用する

A を見直す条件。

- cloud session や CI の agent で共有 skill を使いたくなった
- 自分以外が repo で agent を使うようになった
- global skill の変更が特定 repo の作業を壊す事故が起きた

### 3. 設計

#### 3-1. 二層モデルと判定基準

- global tier: dotfiles `.agents/skills/<name>/`。どの repo でも同じ手順で成立する skill
- repo tier: 各 repo の `.agents/skills/<name>/`。その repo の content / infra / 契約に結び付いた skill

global に置く条件。新規作成と昇格 (repo tier からの移設) のときに適用する。

1. 本文が repo 固有の path / host / command / file 名を手順の一部として持たない (事例としての言及は可)
2. 2 つ以上の repo で使う見込みがある
3. 公開してよい内容である (dotfiles は PUBLIC)
4. 依存する他の skill / agent / script が global 側に揃っている

既知の例外: dotfiles 専用の `install-creator` / `permission-sync` は条件 2 を満たさないが global に見えている。dotfiles の `.claude/` が project 設定と home 設定の正本を兼ねる構造に由来し、この plan では直さない。

#### 3-2. binding (repo 固有の値の置き場所)

- repo 固有の値は `<repo>/.agents/bindings/<skill>.md` に置く。`<repo>` は操作対象の Git worktree root (`git rev-parse --show-toplevel`) で、subdirectory から起動しても同じ file を読む
- global skill は最初にこの file の有無を確認し、あれば読む
- README / AGENTS.md に既にある規約 (検証 command、commit / push 規約) は複製しない。binding からその節を名前で参照する。新たに切り出す固有規約だけ binding を正本にする
- binding が無い repo で許す操作を skill ごとに定める。確定できない値があれば、変更を行う前に止まる
- mozaic.fm の `docs` skill の監査対象 (`docs/SKILL.md:66-71`) に binding と参照先の節を加える
- 初稿は「拡張機構は作らない」としたが、`writing` / `sync` / `skill` の repo 依存の量を見て改めた。README に足すと毎 session の context を消費し、「repo の文書」では読む場所が定まらない

#### 3-3. 同名禁止

- global と repo tier に、別実体で同じ `name` を置かない。Claude では repo 側が黙って隠れ、Codex では 2 つ出る
- 同時に読まれない repo 同士の同名は許す
- 検査は `bin/skill-check` (4-3) が行う
- 移設中に限り、移設対象の名前の二重配置を許す (5 章)

#### 3-4. home 側の配線

- `~/.agents/skills` -> `$HOME/dotfiles/.agents/skills` の dir symlink を slink.sh で張る。`~/.agents/` 自体は実 directory のまま残す
- `~/.claude/agents` と `~/.codex/agents` は dotfiles の `.claude/agents` / `.codex/agents` への dir symlink にする
- `~/.codex/skills/` からは user skill を退避し、`.system/` だけを残す。per-skill symlink の loop は削除する
- Claude 側の `~/.claude/skills` は変更しない
- repo 内の `.codex/skills` (dotfiles と jxck.io) は不要だが害も無いので触らない

#### 3-5. `skill` と `agent-maintainer` の統合

- global の `skill` に一本化し、`agent-maintainer` は削除する (TBD-4)
- subcommand の責務: `new` (作成) / `fix` (修復) / `list` (global と repo の両方を一覧) / `check` (監査。機械検査は `bin/skill-check`) / `promote <name>` (repo tier から global への移設 = 5 章の手順)
- `new` と `fix` は作成先 repo の配線規約を先に読む。dotfiles は dir symlink、mozaic.fm は Claude のみ per-skill symlink、jxck.io は両 tool の per-skill symlink である
- `new` の最初に「global か repo か」を 3-1 の条件で判定する
- repo 固有の記述 (`pnpm fmt:check`、README の directory 表) は mozaic.fm の binding へ移す

#### 3-6. subagent 定義の global 化

- 6 定義 (Claude 3 + Codex 3) を公開審査し、検証の指示を「repo の AGENTS.md が定める検証」に一般化してから dotfiles に置く
- subagent は、それを参照する skill より先に配る
- mozaic.fm 側の同名定義は削除する。Claude では project が user に勝つので、残すと global 側の更新が mozaic.fm でだけ効かない
- `planning` skill の fallback 記述 (`planning/SKILL.md:114`) を同じ commit で追従する

#### 3-7. 公開範囲

- 審査の対象は SKILL.md だけでなく、付随 file (`measure.py` 等) と agent 定義も含める
- 見る点: host 名 / IP / 鍵の運用手順 / 非公開 plan からの引用 / 第三者の情報
- 審査で落ちた記述は、一般化して書き直すか mozaic.fm の binding に残す
- git 履歴は引き継がない
- dotfiles 側の commit message に private repo の名前と commit hash を書かない。対応は mozaic.fm 側の削除 commit に「dotfiles の commit `<hash>` へ移設」と書いて残す

#### 4-3. `bin/skill-check` (zsh、`-h` 付き)

- 引数は skill root (`.agents/skills` の path)。先頭を global、以降を repo として扱う。指定した root が 1 つでも無ければ非 0
- 検査
  - 各 `SKILL.md` の frontmatter `name` と directory 名の一致 (引用符付きの値を扱う)
  - global と各 repo の組ごとの、別実体での `name` 衝突。同じ実体への別経路は 1 件と数える
  - SKILL.md の無い directory の報告 (`synced/` と `.trash/` は管理用として無視する)

- fixture: 引用符付きの値 / 同一実体への別経路 / 別実体の衝突 / root 欠落 / 空 directory / 配線の欠落・余分・宛先違い・dangling。それぞれ期待どおりの終了 code になること
