# 構造のルール

[SKILL.md](SKILL.md) の「構造のルール」の本体である。ルールごとに、悪い例と直した例を示す。

## リスト記法内で改行しない

例えば以下のような書き方はしない。

```md
6. 節ごとに書き直す。1 回の編集で全体を書き換えない
7. `git diff` の消えた行を 1 行ずつ見る。
   数値、パス、コマンド、link の宛先、否定形、既定値、例外条件を特に見る。
   syntax の gate は全て通るのに条件だけが落ちる、という壊れ方をする
8. その chunk の gate を通す。chunk ごとに通し、最後にまとめてではない
```

7. が複数行に改行している。この場合はリストをネストさせる。

```md
6. 節ごとに書き直す。1 回の編集で全体を書き換えない
7. `git diff` の消えた行を 1 行ずつ見る
   - 数値、パス、コマンド、link の宛先、否定形、既定値、例外条件を特に見る
   - syntax の gate は全て通るのに条件だけが落ちる、という壊れ方をする
8. その chunk の gate を通す。chunk ごとに通し、最後にまとめてではない
```

`<ol>` だけでなく `<ul>` でも同じである。以下のような書き方はしない。

```md
- `http://localhost:3000` で起動する。
  dev server が API を同じ process に mount している。設定は `server.config.ts` が
  毎 request 読み直すため、server code の編集は再起動なしで反映される
- `predev` が生成物を自動生成する。対象は `dist/content/` 配下の記事 JSON、
  検索用の `dist/search-index.json`、`dist/sitemap.xml` である。
  記事の Markdown を編集したら dev を再起動する。
  `build:content` だけでは検索 index と sitemap は更新されない
```

ネストしたリストにする。ネストする際に、長い一文は主張ごとの文に区切る。

```md
- `http://localhost:3000` で起動する
  - dev server が API を同じ process に mount している
  - 設定は `server.config.ts` が毎 request 読み直す
  - server code の編集は再起動なしで反映される
- `predev` が生成物を自動生成する
  - 対象は次の 3 つである
    - `dist/content/` 配下の記事 JSON
    - 検索用の `dist/search-index.json`
    - `dist/sitemap.xml`
  - 記事の Markdown を編集したら dev を再起動する
  - `build:content` だけでは検索 index と sitemap は更新されない
```

## リストの見出し項目に本文を続けない

「**見出し**: 説明」の形で、見出しと同じ行に本文を続けない。見出しは単独の行にして、説明は子に下げる。

例えば以下のような書き方はしない。

```md
- **`playwright install` は Node 22 で実行する**: Node 26 だと zip 展開中に全スレッドがイベント待ちのままデッドロックする (2 回再現済み)
  - `mise x node@22 -- pnpm exec playwright install chromium firefox webkit`
```

見出しだけを走査して目的の項目を探せるように、説明は全て子に置く。

```md
- **`playwright install` は Node 22 で実行する**
  - Node 26 だと zip 展開中に全スレッドがイベント待ちのままデッドロックする (2 回再現済み)
  - `mise x node@22 -- pnpm exec playwright install chromium firefox webkit`
```

## リスト項目を接続助詞で繋げない

1 つの bullet に「を含み、」「のため、」「であり、」で複数の主張を詰めない。主張ごとに bullet を分ける。

例えば以下のような書き方はしない。

```md
- `check.yml` は lint、typecheck、unit test、build を含み、editor の検査は unit test に統合済みで、2026-08 の整理で対応した
```

主張は 2 つある。分ける。時期の補足は子に下げる。

```md
- `check.yml` は lint、typecheck、unit test、build を含む
- editor の検査は unit test に統合済みである
  - 2026-08 の整理で対応した
```

理由や補足は同じ階層に並べず、子の bullet に下げる。

```md
- 音声 file が手元になくても再生は動く
  - file 名を公開 URL に解決するため
```

## 読点で改行しない

例えば以下のような書き方はしない。

```md
計測は `measure.py` が持つ。grep と句点 split では測れない。
Markdown の link や code span の括弧を数えてしまい、
空行や fence を跨いで段落が 1 文に連結されるからである。
```

2 行目が読点で改行している。この改行はいらない。

```md
計測は `measure.py` が持つ。grep と句点 split では測れない。
Markdown の link や code span の括弧を数えてしまい、空行や fence を跨いで段落が 1 文に連結されるからである。
```

## 改行は文と話題の切れ目に置く

幅を揃えるためだけに文の途中で折り返さない。前節の読点での改行はその典型である。
行の切れ目は話題の切れ目に合わせる。同じ話題の文は同じ行に続け、話題が変わるところで改行する。

例えば以下のような書き方はしない。

```md
この package は社内専用で運用する。2026-07-20 の決定で、registry への公開はしない。
ライセンスも明示しない。文書と画像は作者の著作物のため、二次配布は許可しない方針である。
```

2 行目の「ライセンスも明示しない」は 1 行目の社内専用の決定の続きで、後ろの著作物の話とは切れている。行を話題に合わせて割り直す。

```md
この package は社内専用で運用する。2026-07-20 の決定で、registry への公開はしない。ライセンスも明示しない。
文書と画像は作者の著作物のため、二次配布は許可しない方針である。
```

話題が変わるところには空行を置き、段落として分ける。
行の長さを理由に文の途中で折り返さない。長さへの対処は文自体の分割であって、source 上の折り返しではない。

## 1 段落 1 話題にする

読点で繋いだ長文を割るのと同じ判断を、段落にも適用する。複数の話題を 1 段落に詰めると、どれも同じ重さに見えて読み飛ばされる。

例えば以下は、2 つの問題とその共通の根が 1 段落に入っている。

```md
Web platform の進化に開発者の実践が追いつかない 2 つの問題を扱った。Baseline になって久しい機能の polyfill を出荷し続ける「sticky polyfill」問題 (IntersectionObserver polyfill は Baseline 到達から 6.5 年たっても週 210 万ダウンロードある) と、Baseline 前の新機能の採用をためらう「reluctant adoption」問題である。両者の共通の根は機械可読なデータソースが無いことだとした。
```

話題ごとに割る。あわせて、括弧に押し込んだ数値を本文へ出す。

```md
Web platform の進化に開発者の実践が追いつかない 2 つの問題を扱った。

一つは「sticky polyfill」問題である。Baseline になって久しい機能の polyfill を、出荷し続ける。IntersectionObserver の polyfill は、Baseline 到達から 6.5 年たっても週 210 万ダウンロードある。もう一つは「reluctant adoption」問題で、Baseline 前の新機能の採用をためらう。

両者の共通の根は機械可読なデータソースが無いことだとした。
```

密な段落が 2-3 個続いたら、短い段落を 1 つ置く。
短い段落の役割は、確定した事実の固定、次に判定する対象の提示、視点の遠近の切替のいずれかに限る。「次は〜を見る」のような進行の予告には使わない。

## だ、である調を徹底する

例えば以下のような書き方はしない。

```md
manifest の手順に「1 ファイルだけを直すときは manifest を作らず、そのファイルを渡す」を足しました。
```

「です、ます調」を使っている。「だ、である調」で書く。

```md
manifest の手順に「1 ファイルだけを直すときは manifest を作らず、そのファイルを渡す」を足した。
```

## ラベルと体言止めを文にする

主張や決定を「ラベル: 内容」の形や、link で終わる体言止めに載せない。述語まで書いて文にする。

例えば以下のような書き方はしない。

```md
例外: [`lib/router/`](lib/router/) (自前の router ライブラリ) のみ MIT である。
詳細は [docs/README.md](docs/README.md)。
```

「例外」はこの文の主張そのものであり、ラベルに逃がすと文が断片になる。同格の括弧は連体修飾に開く。
決定の宣言は「とする」と書き、事実の記述の「である」と区別する。

```md
例外として、自前の router ライブラリである [`lib/router/`](lib/router/) のみ MIT とする。
詳細は [docs/README.md](docs/README.md) を参照する。
```

`plan: [公開手順](../plan/20260721-publish.md)` のような出典の pointer と、「一覧: `/`」のような key-value のデータは、ラベルのままでよい。

## 複数あるならリストで列挙する

例えば以下のような書き方はしない。

```md
完了の条件は 3 つある。gate が exit 0 であること。`git diff` に事実の欠落がゼロであること。閾値の超過を残すなら、その理由が報告に書かれていること。
```

3 つあるならリストで列挙する。

```md
完了の条件は 3 つある。

- gate が exit 0 であること
- `git diff` に事実の欠落がゼロであること
- 閾値の超過を残すなら、その理由が報告に書かれていること
```

リスト項目内のインライン列挙も同じで、スラッシュや括弧で横に並べず、ネストで開く。値の注釈はラベルに反転させる。

```md
- 確認用 URL: `/` (一覧) / `/posts/200.html` (詳細) / `/search?q=monthly` (検索)
```

```md
- 確認用 URL
  - 一覧: `/`
  - 詳細: `/posts/200.html`
  - 検索: `/search?q=monthly`
```

## できるだけ表は使わない

Markdown の表は、エディタ上では読みにくい。特に 2 列しか無い場合は、表を使わないで書く。

```md
| 対象           | 通す gate                             |
| -------------- | ------------------------------------- |
| すべて         | `make fmt-check`                      |
| `README.md`    | link 切れが無いこと                   |
| skill          | frontmatter の `name` が不変であること |
| コードコメント | `make typecheck`                      |
```

これは、リストのネストだけで表現できる。

```md
- すべて
  - `make fmt-check`
- `README.md`
  - link 切れが無いこと
- skill
  - frontmatter の `name` が不変であること
- コードコメント
  - `make typecheck`
```

表は、列が 3 つ以上あり、行を横に見比べる必要があるデータに使う。

## コードコメントにも同じ構造ルールを適用する

対象は Markdown だけでなく、TypeScript / JavaScript / Shell / Makefile / YAML のコメントも含む。
上記の構造ルールのうち、次はコメントにもそのまま適用する。

- 読点で改行しない
- 改行は文と話題の切れ目に置く
- だ、である調を徹底する
- ラベルと体言止めを文にする
- リスト記法内で改行しない
  - `- ` で始まる箇条書き形式のコメントブロックが対象

「できるだけ表は使わない」は Markdown の記法に依存するため、コメントには適用しない。

コメントの目的そのもの、つまり書くか書かないか、WHAT でなく WHY を書くかの判断は、この skill の対象外である。
repo の AGENTS.md / CLAUDE.md のコーディング規約が正であり、この skill は書くと決めたコメントの文章構造だけを扱う。
